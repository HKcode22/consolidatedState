# ConsolidatedState — Bank Statement Consolidator

A small web application that converts bank-statement PDFs into one validated consolidated report.

## Product goal

The tool is **not hardcoded to one bank**. It detects the structural layout of a statement and selects a generic parsing strategy.

```text
1–12 PDF statements
        ↓
PDF inspection + coordinate-aware extraction
        ↓
Detect statement layout family
        ↓
Generic parsing strategy
        ↓
Normalized transactions
        ↓
Validation / reconciliation
        ↓
Preview
        ↓
Consolidated Excel workbook
```

## Current generic layout strategies

### 1. Running-ledger layout

For statements structurally similar to:

```text
Date | Description/Details | Debit | Credit | Balance
```

The strategy uses PDF coordinates to locate the columns. It does not check for a particular bank name.

### 2. Sectioned activity layout

For statements structurally similar to:

```text
Deposits / Credits / Additions
Date | Description | Amount

Withdrawals / Debits / Subtractions
Date | Description | Amount
```

### 3. Single Amount + running Balance layout

For statements structurally similar to:

```text
Date | Description | Amount | Balance
```

Debit/credit direction is accepted only when it is explicit (+/-, CR/DR) or mathematically proven by the running-balance movement.

Detection is based on layout and financial headings, not bank identity. Additional layout families can be added without changing the normalization, validation, or export layers.

## What "any bank" means

No deterministic parser can honestly guarantee every PDF generated by every bank in the world. Statements can be scanned images, use unusual fonts, omit standard columns, use different languages, or have entirely different layouts.

The design therefore aims for **broad bank-agnostic support with safe fallback**:

1. recognize known structural families automatically;
2. parse them without bank-specific names;
3. verify the extracted transactions mathematically;
4. refuse export when the document cannot be interpreted safely;
5. add another generic layout strategy when a genuinely new structure appears.

This lets coverage grow over time without turning the project into a collection of hardcoded bank-name rules.

## MVP stack

- **UI + app server:** Streamlit / Python
- **PDF text and geometry:** PyMuPDF
- **Data processing:** pandas
- **Excel output:** openpyxl
- **Tests:** pytest
- **Source of truth:** GitHub
- **Deployment:** Replit

No LLM, paid API, GPU, Firebase database, or vector database is required.

## Safety rules

Financial arithmetic is deterministic.

The application must never:

- invent a missing transaction;
- silently change a dollar amount;
- guess debit vs credit when the structure is ambiguous;
- export a partial consolidation when one input failed.

Unknown or unreconciled statements are blocked for review.

Cross-statement validation also checks detected account identity, explicit currency, statement-period overlap/gaps, and adjacent opening/closing balance continuity. Numeric dates are interpreted as MM/DD or DD/MM only when the order can be inferred safely; ambiguous dates are not guessed.

Money arithmetic uses `Decimal`, not binary floating point.

## Output workbook

The final `.xlsx` report contains:

- `Transactions` — normalized transactions in chronological order
- `Monthly Summary` — debit, credit, and net totals by month
- `Validation` — intake, parser, transaction-integrity, and reconciliation checks
- `About` — report disclaimer and generation notes

The output is a **consolidated report derived from source statements**, not an official bank-issued statement.

## Privacy

**Never commit real bank statements, account/routing numbers, extracted statement text, or generated reports to GitHub.**

PDFs are intended to be processed in memory. Real statement examples are used only to validate layout strategies; the repository contains code and synthetic tests, not the private documents.

## Next expansion

As more representative statements arrive:

- test whether an existing structural strategy recognizes them;
- if not, identify the new layout family;
- implement that family generically;
- add synthetic regression tests;
- consider OCR for image-only/scanned PDFs.

The goal is increasing layout coverage, not hardcoding individual banks.
